# 로드 테스트 실험 전제 및 가정

## 문서 개요

본 문서는 Eatda 서버의 로드 테스트 환경 구성에 대한 전제 조건, 가정, 그리고 실제 프로덕션 환경과의 비교를 정리합니다.

**작성일**: 2026-06-26  
**대상 환경**: AWS EC2 t3.medium 기준  
**테스트 목적**: 프로덕션 배포 전 성능 검증 및 임계점 파악  
**시나리오**: 초기 서비스 (론칭 후 6개월~1년) — 빠른 성장 초기 단계

## 1. 목표 프로덕션 환경

### 1.1 AWS EC2 인스턴스 사양

#### 기준 인스턴스: **t3.medium**

```
인스턴스 타입: t3.medium
vCPU:          2
메모리:        4 GiB
네트워크:      Up to 5 Gigabit
스토리지:      EBS gp3 (3000 IOPS, 125 MB/s)
월 예상 비용:  ~$30 (약 40,000원)
```

#### 선택 이유

- ✅ **적절한 성능**: 소규모 프로덕션 서비스에 적합
- ✅ **비용 효율**: 스타트업/초기 단계에서 감당 가능한 비용
- ✅ **확장 가능**: 트래픽 증가 시 t3.large, m5.large로 수직 확장 용이
- ⚠️ **Burstable 성능**: CPU 크레딧 기반으로 일시적 트래픽 증가 대응 가능

#### t3.small과의 비교

| 항목 | t3.small | t3.medium (선택) |
|------|----------|------------------|
| vCPU | 2 | 2 |
| 메모리 | 2 GiB | 4 GiB |
| JVM Heap | 최대 1.5GB | 최대 2.5GB |
| 여유 메모리 | 부족 (OOM 위험) | 충분 |
| 월 비용 | ~$15 | ~$30 |

**결론**: 안정성을 위해 메모리 여유가 있는 **t3.medium 선택**

## 2. 테스트 환경 구성

### 2.1 Docker 컨테이너 리소스 제한

```yaml
# docker-compose.load-test.yml
app:
  cpus: 2.0              # t3.medium의 2 vCPU
  mem_limit: 4g          # t3.medium의 4 GiB
  mem_reservation: 3g    # 최소 3GB 보장
```

### 2.2 JVM 설정

```yaml
JAVA_OPTS:
  -Xms2g                      # 초기 Heap 2GB
  -Xmx2.5g                    # 최대 Heap 2.5GB (메모리의 62.5%)
  -XX:+UseG1GC                # G1 Garbage Collector
  -XX:MaxGCPauseMillis=200    # 최대 GC 일시 정지 목표 200ms
  -XX:MaxMetaspaceSize=256m   # Metaspace 최대 256MB
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/tmp/heap_dump.hprof
```

#### 메모리 구성 (총 4GB)

| 영역 | 크기 | 비율 | 용도 |
|------|------|------|------|
| **JVM Heap** | 2.5 GB | 62.5% | 애플리케이션 객체 저장 |
| **Metaspace** | ~256 MB | 6.25% | 클래스 메타데이터 |
| **Thread Stack** | ~200 MB | 5% | 스레드당 1MB × ~200 스레드 |
| **Direct Buffer** | ~300 MB | 7.5% | NIO, Netty 등 |
| **Native Memory** | ~250 MB | 6.25% | JVM 내부 구조 |
| **OS & Buffer** | ~500 MB | 12.5% | OS 캐시, 여유 공간 |

### 2.3 데이터베이스

```yaml
MySQL 8.0:
  메모리: 무제한 (테스트 환경)
  최대 연결: 1000
  Character Set: utf8mb4
  
실제 프로덕션 예상:
  AWS RDS db.t3.small (2 vCPU, 2 GiB)
  또는 db.t3.medium (2 vCPU, 4 GiB)
```

### 2.4 스토리지

```yaml

  로컬 파일시스템 사용
  
실제 프로덕션:
  AWS S3 Standard
  이미지 저장 및 Presigned URL 제공
```

## 3. 실험 전제 조건

### 3.1 테스트 환경 가정

#### ✅ 동일하거나 유사한 조건

1. **CPU 코어 수**: 2 vCPU (정확히 동일)
2. **메모리 용량**: 4 GB (정확히 동일)
3. **JVM 설정**: 프로덕션과 동일한 GC 및 힙 설정
4. **애플리케이션 코드**: 프로덕션과 동일한 빌드
5. **데이터베이스 스키마**: 프로덕션과 동일

#### ⚠️ 차이가 있는 조건

1. **네트워크 지연**:
   - 테스트: 로컬 컨테이너 간 통신 (< 1ms)
   - 프로덕션: 실제 네트워크 지연 (5-50ms)
   - **영향**: 응답 시간이 프로덕션에서 5-50ms 추가 예상

2. **디스크 I/O**:
   - 테스트: 호스트 SSD 공유 (높은 IOPS)
   - 프로덕션: EBS gp3 (3000 IOPS)
   - **영향**: DB 쿼리 성능 차이 발생 가능

3. **외부 API 호출**:
   - 테스트: Mock 사용 (즉시 응답)
   - 프로덕션: 실제 Kakao API (100-500ms)
   - **영향**: OAuth 로그인, 지도 검색 시 지연 발생

4. **S3 저장소**:
   - 테스트: LocalStack (로컬 파일시스템)
   - 프로덕션: AWS S3 (네트워크 기반)
   - **영향**: 이미지 업로드/조회 지연 추가

5. **CPU 성능 모델**:
   - 테스트: **일정한 성능** (Docker cpus 제한)
   - t3.medium: **Burstable 성능** (CPU 크레딧 기반)
   - **영향**: 프로덕션에서 CPU 크레딧 소진 시 성능 저하 가능

### 3.2 CPU 크레딧 (Burstable 성능)

#### t3.medium CPU 크레딧 메커니즘

```
기본 CPU 사용률: 20% (0.4 vCPU)
크레딧 축적: 시간당 24 크레딧
크레딧 소진: 100% 사용 시 시간당 120 크레딧 소모
초기 크레딧: 288 크레딧 (2.4시간 분량)
최대 크레딧: 288 크레딧
```

#### 크레딧 소진 시나리오

| 시나리오 | CPU 사용률 | 크레딧 소모 | 지속 가능 시간 |
|---------|-----------|------------|--------------|
| 평상시 | 20% | 0 (축적) | 무제한 |
| 중간 부하 | 50% | 시간당 36 | ~8시간 |
| 높은 부하 | 80% | 시간당 72 | ~4시간 |
| 최대 부하 | 100% | 시간당 120 | ~2.4시간 |

**크레딧 소진 후**: CPU 사용률이 20%로 제한되어 성능 급격히 저하

#### 테스트 시 고려사항

- ✅ 로드 테스트는 CPU 100% 상황을 시뮬레이션
- ⚠️ 프로덕션에서는 지속 불가능 (크레딧 관리 필요)
- 💡 지속적인 높은 부하 예상 시 m5.large (Burstable 없음) 고려

| **OAuth 로그인** | 50ms | 300-800ms | +250-750ms (외부 API) |

## 5. 테스트 시나리오

### 기본 전제: 뽈레(Polle) 벤치마크

```
서비스 규모: 니치 버티컬 미식가 커뮤니티
누적 가입자: 12만 명 (2017년 론칭 후 9년 운영)
MAU: 3만 명 (DAU/MAU 비율 40%)
DAU: 12,000명

🎯 테스트 시나리오 시간 축: 초기 서비스 (론칭 후 6개월~1년)
   
   이유:
   - 빠른 테스트 반복 (데이터 생성 10분 vs 성숙 서비스 1시간)
   - 초기 서비스 안정성 검증이 우선 목표
   - 병목 지점 발견은 데이터 규모와 무관 (N+1 쿼리, 캐싱 부재 등)
   - 120,000개 Cheer로도 인덱스/쿼리 최적화 충분히 검증 가능
   
   참고: 성숙 서비스 (2~3년 운영) 시에는 Cheer 500,000개, Story 100,000개 예상
        → 추후 대규모 데이터 성능 검증 필요 시 별도 스크립트 제작

테스트 데이터 규모 (초기 서비스 6개월~1년 기준):
  - Member: 50,000명 (초기 빠른 성장 가정, 월 평균 4,000~5,000명 가입)
  - Store: 10,000개 (니치 미식가 커뮤니티에 적합한 규모)
  - Cheer: 120,000개 (Store당 평균 12개, 초기 사용자 활성도 높음)
  - Story: 30,000개 (리뷰 작성 습관 형성 중, Member당 평균 0.6개)
  - CheerImage: ~180,000개 (Cheer당 평균 1.5개)
  - StoryImage: ~60,000개 (Story당 평균 2개)
  - CheerTag: ~300,000개 (Cheer당 평균 2.5개)

일일 사용자 세션:
  - 총 사용자 세션: 12,000 세션/day
  - 평균: 0.14 세션/s
  - 피크(점심 11:30-13:30, 저녁 18:00-21:00): 0.42-0.7 세션/s (평균 대비 3-5배)
  - 일반 시간(오전/오후): 0.17-0.28 세션/s
  - 오프피크(새벽/심야): 0.02-0.07 세션/s

트래픽 패턴 특성:
  - 맛집 검색 서비스 → 식사 시간 전후 집중
  - 점심/저녁 피크 5시간: ~60% 트래픽 집중
  - 새벽/심야 12시간: ~10% 트래픽

프론트엔드 API 호출 패턴 (1명당):
  - 홈 탭 진입: 3개 API 동시 호출
  - 가게 상세 진입: 4개 API 동시 호출
  - 마이 탭 진입: 3개 API 동시 호출
  - 평균 페이지뷰: 3-5 페이지/세션
  → 1명의 사용자 = 평균 10-15 req 생성
```

### 5.1 시나리오 1 — 평상시 운영 (Baseline)

**목표**: 일상적인 사용 패턴 시뮬레이션

```
트래픽 프로필:
  - 평균: ~4 req/s
  - 일반 시간대(오전/오후): ~5-8 req/s
  - 오프피크(새벽/심야): ~1-2 req/s

동시 사용자: 50-100명
지속 시간: 10분
예상 CPU: 20-40% (크레딧 축적)

주요 검증 사항:
  - 기본 HikariCP 10개 커넥션으로 충분한가?
  - N+1 쿼리 발생 여부 (batch_fetch_size=30 검증)
  - 외부 API 호출(가게 검색) 빈도 (일 ~100회)
```

**예상 병목**: 없음 (서버 여유 충분)

### 5.2 시나리오 2 — 핫플레이스 집중 트래픽 (점심 피크)

**목표**: 점심시간 특정 가게 상세 페이지 트래픽 집중 시뮬레이션

```
배경: 
  - 성수동 신상 맛집이 미식가들 사이에서 화제
  - 점심시간(12:00-12:30) 인플루언서 공유 후 집중 조회

트래픽 패턴:
  - 기본 피크 트래픽: 15 req/s
  - 단일 store_id 집중 조회: 추가 10 req/s
  - 프론트엔드가 상세 진입 시 4개 API 동시 호출:
    1. GET /api/shops/{id}
    2. GET /api/shops/{id}/cheers?size=10
    3. GET /api/shops/{id}/images
    4. GET /api/shops/{id}/tags
  - 총 동시 요청: 15 + (10 × 4) = 55 req/s

지속 시간: 30분 (점심 피크)
예상 CPU: 60-80%

주요 검증 사항:
  - N+1 쿼리 폭발 여부 (Store → Cheer → CheerImage lazy 로드)
  - batch_fetch_size=30 실효성
  - DB CPU 스파이크 발생 여부
  - S3 이미지 URL 응답 지연 (이미지 개수 많을 경우)
```

**예상 병목**: N+1 쿼리, 캐싱 부재

### 5.3 시나리오 3 — SNS 바이럴 트래픽 (저녁 피크)

**목표**: 저녁시간 특정 리뷰가 SNS에서 공유되어 트래픽 급증

```
배경:
  - 뽈레 특정 리뷰가 SNS(카톡방, 블로그)에서 공유
  - 저녁시간(19:00-20:00) "이 리뷰 읽고 싶어!" 클릭 몰림

트래픽 패턴:
  - 기본 저녁 피크: ~18 req/s
  - 바이럴 추가 유입: ~30 req/s
  - 총: ~50 req/s (피크 대비 2.5-3배)
  
  - 주요 경로:
    * 홈(/) 진입 → GET /api/stories (40%)
    * 특정 리뷰 상세 → GET /api/stories/{id} (30%)
    * 해당 가게 상세 → GET /api/shops/{id} (20%)
    * 댓글 조회 → GET /api/stories/{id}/comments (10%)

50 req/s 중 40% = 20 req/s on GET /api/stories?size=20

동시 사용자: 300-600명
지속 시간: 1시간 (저녁 피크)
예상 CPU: 70-90%

주요 검증 사항:
  - GET /api/stories?size=20 반복 DB 히트 (캐싱 부재)
  - 24개 스토리 × 각 이미지 + 작성자 정보 lazy 로드
  - DB 커넥션 풀 사용률 (20 req/s × 50ms = 1개, 충분하나 여유 적음)
  - N+1 쿼리 반복으로 인한 DB CPU 부하
```

**예상 병목**: 캐싱 부재, N+1 쿼리 반복

### 5.4 시나리오 4 — 쓰기 트래픽 집중 (이벤트/챌린지)

**목표**: 이벤트 기간 중 리뷰/이미지 업로드 집중

```
배경:
  - "이번 주 최고의 맛집 리뷰 공모전" 기간
  - 저녁 피크 시간(18:00-21:00)에 리뷰/이미지 업로드 집중

트래픽 패턴:
  - 평상시 저녁 피크 읽기: ~18 req/s
  - 이벤트 쓰기 추가: ~40-60 req/s
  - 총: ~60-80 req/s
  
  - 주요 API:
    * POST /api/stories: 리뷰 등록 (30%)
    * POST /api/image/presigned-url: S3 업로드 URL 발급 (40%)
    * PUT {presignedUrl}: S3 직접 업로드 (서버 부하 없음)
    * POST /api/cheer: 응원 등록 (30%)

동시 사용자: 600-1000명
지속 시간: 3시간 (저녁 피크)
예상 CPU: 80-100% (크레딧 소진 위험)

주요 검증 사항:
  - DB 커넥션 풀 고갈 (80 req/s × 500ms = 40개 필요, 기본값 10개)
  - S3 이동 로직이 @Transactional 내부인가? (커넥션 장시간 점유)
  - 카카오 OAuth 의존성 (신규 유저 로그인 집중)
  - 동일 가게 응원 시 락 경합 (Store 엔티티 업데이트)
```

**예상 병목**: DB 커넥션 풀 부족, S3 트랜잭션 내부 처리, OAuth 지연

### 5.5 시나리오 5 — OAuth 장애 (외부 의존성 장애 전파)

**목표**: 점심 피크 시 카카오 OAuth 서버 장애 시 전체 서비스 영향 확인

```
배경:
  - 점심시간(12:00) 카카오 OAuth 서버 장애
  - 모든 로그인 요청이 타임아웃

트래픽 패턴:
  - 점심 피크 전체: 15 req/s
  - 그 중 로그인 요청: 3-5 req/s (신규 유저 + 재로그인)
  
OAuth 응답 시간:
  - 정상: 200-500ms
  - 장애: 타임아웃 5초 (또는 무한 대기)

지속 시간: 10분 (장애 시간 가정)
예상 CPU: 변동 없음 (I/O 대기)

주요 검증 사항:
  - 스레드 블로킹 (5 req/s × 5s = 25개 스레드 점유)
  - Tomcat 스레드 풀 고갈 (기본 200개 중 12.5% 점유)
  - 다른 정상 API 요청도 지연 발생하는가?
  - 타임아웃 미설정 시 무한 대기 → 전체 서비스 마비
  - Circuit Breaker 적용 여부
```

**예상 병목**: 외부 API 장애 전파, 스레드 풀 고갈

### 5.6 시나리오 6 — DB 슬로우 쿼리 발생

**목표**: 특정 쿼리가 예상보다 오래 걸려 커넥션 풀 고갈

```
배경:
  - 복잡한 필터링/정렬 쿼리
  - 인덱스 미적용 시 Full Table Scan

트래픽 패턴:
  - 평상시: 모든 쿼리 50ms 이내
  - 슬로우 쿼리 발생: 특정 API의 쿼리가 5초 소요
  - 예시: GET /api/stories?district=성수동&sort=latest&size=50

10 req/s × 5s = 50개 커넥션 필요

지속 시간: 5-10분 (쿼리 개선 전)
예상 CPU: 40-60% (DB CPU 높음)

주요 검증 사항:
  - HikariCP 커넥션 풀 고갈 (기본값 10개)
  - 11번째 요청부터 대기 (connection-timeout: 30초)
  - 30초 후 타임아웃 에러 (HTTP 500/504)
  - 다른 정상 API도 커넥션을 얻지 못해 실패
  - Slow query log로 원인 쿼리 식별 가능한가?
```

**예상 병목**: DB 커넥션 풀 고갈, 슬로우 쿼리 감지 지연

### 5.7 지속성 테스트 (Endurance)

**목표**: 장시간 운영 시 메모리 누수 확인

```
동시 사용자: 100명
요청 빈도: 20 req/sec
지속 시간: 30분-1시간
모니터링: JVM Heap, GC 빈도
```

## 7. 제약 사항 및 한계

### 7.1 테스트 환경의 한계

1. **네트워크 비현실성**: 실제 인터넷 환경 미반영
2. **외부 의존성**: Kakao API 등 실제 호출 없음
3. **데이터 규모 시간 축**: 초기 서비스 (6개월~1년) 기준, 성숙 서비스 (2~3년) 데이터량 미달
4. **지리적 분산**: 다양한 지역에서의 접속 미고려
5. **실제 사용 패턴**: 사용자 행동의 무작위성 부족

### 7.2 보상 방법

| 한계 | 보상 방법 |
|------|----------|
| 네트워크 지연 부재 | 응답 시간 목표를 보수적으로 설정 (50% 여유) |
| Mock 사용 | 외부 API 지연 시간을 고의로 추가 (sleep) |
| CPU 크레딧 | 연속 부하 테스트로 크레딧 소진 시뮬레이션 |
| 초기 서비스 데이터 규모 | Member 50,000명, Cheer 120,000개, Story 30,000개 (초기 6개월~1년 기준, 빠른 테스트 반복 가능). 병목 지점 발견은 데이터 규모와 무관. 성숙 서비스 (2~3년) 검증 필요 시 별도 대규모 데이터 스크립트 제작 |

## 9. 의사결정 기준

### 9.1 프로덕션 배포 결정

✅ **배포 가능** (다음 조건 모두 충족):
- [ ] 정상 트래픽에서 평균 응답 시간 < 200ms
- [ ] 피크 트래픽에서 에러율 < 1%
- [ ] 스트레스 테스트에서 Graceful Degradation 확인

- [ ] 모든 성공 기준 충족

⚠️ **추가 최적화 필요** (다음 중 하나라도 미충족):
- [ ] P99 응답 시간 > 2000ms
- [ ] 에러율 > 1%
- [ ] 메모리 사용률 > 80%
- [ ] OOM 발생

🚨 **인스턴스 업그레이드 필요** (다음 증상 발생):
- [ ] CPU가 지속적으로 80% 이상
- [ ] 메모리 부족으로 잦은 Full GC
- [ ] 크레딧 소진으로 성능 급격히 저하
- [ ] 처리량이 목표의 50% 미만
